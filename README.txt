Куда — JMeter 5.6.3

Откройте kuda.jmx. Весь Groovy-код находится внутри элементов JSR223.
План рассчитан на один экземпляр JMeter. Очереди передаются в памяти этой JVM.

Настройки находятся в User Defined Variables «Параметры».
mode=load — основной профиль. stageRates=2|4|8|16 — новые комнаты в минуту.
stepSeconds=600 — длительность каждой ступени. В Open Model Thread Group
расписание собирается встроенным скриптом «Инициализировать прогон» из этих параметров.
После ступеней следует pause(drainSeconds), по умолчанию 300 секунд.
Полный запуск занимает около 45 минут. Начатые компании получают время завершиться.

Запуск из PowerShell:
  D:\kuda-load-testing\run.ps1 -Mode Smoke
  D:\kuda-load-testing\run.ps1 -Mode Load
Скрипт создаёт отдельную папку результатов для каждого запуска.
При обычном запуске JMX в GUI пути файлов начинаются с ~/out и указывают
на каталог out рядом с JMX. Повторные запуски в те же CSV дописывают строки.

Smoke создаёт одну компанию. Паузы голосования сокращены до 100–200 мс,
опрос — до 500 мс, просмотр — до 25 секунд. Это проверка логики.
В Load голосование идёт с паузами 4–7 секунд, опрос — 4 секунды,
просмотр комнаты — 180 секунд. Организатор плюс три разных гостя.
Одна карточка получает общий like, чтобы сценарий всегда мог выбрать победителя.
Остальные голоса случайны. Дополнительный раунд и вход по короткому коду
в этот профиль не включены.

Приглашённые получают задания из очереди. Стандартный пул — 180 потоков.
Опрос использует отдельный пул из 240 потоков и те же токены пользователей.
Организатор при ожидании завершения голосования делает GET сам.
Его отдельный фоновый опрос в это время приостанавливается.
Часть служебных проверок создаёт дополнительные GET к комнате,
поэтому фактическое число запросов уточняется по results.csv.

roomViewSeconds, joinTimeoutSeconds, votingTimeoutSeconds задают просмотр
и пределы ожидания. Списки пользователей, голоса и статус берутся из ответов API.
Общей таблицы бизнес-состояний комнат нет. В заданиях есть только данные
комнаты и флаги завершения/отмены для остановки связанных потоков.

results.csv — HTTP-запросы и ошибки управляющих шагов.
errors.xml — неуспешные результаты с телами ответов.
rooms.csv — итог каждой компании, roomId, победитель, время и причина ошибки.
Summary Report и Aggregate Report встроены в план.
Дерево результатов отключено по умолчанию для экономии памяти.
Успешные служебные Groovy-шаги исключаются из HTTP-статистики.
Токены не записываются в отдельные файлы.

Ветка backend nt снимает лимиты IP. Лимиты пользователя, комнаты и глобального
поиска кода действуют согласно backend. Профиль использует длинные приглашения.
p95 чтения и голоса оценивается отдельно от времени прохождения всей компании.
План создаёт тестовые гостевые профили и комнаты в текущей локальной базе.

В план добавлена транзакция «Создание комнаты». Её отдельная итоговая строка
также попадает в results.csv. При расчёте HTTP RPS учитывайте строки HTTP-запросов,
а итоговую строку транзакции используйте для времени составного действия.

Управление ошибками упрощено до семи If Controller:
общий блок организатора, блок шагов создания комнаты, общий блок участника,
проверка получения задания опроса, проверка разрешения опроса
и по одной проверке внутри двух циклов голосования.
Общие блоки повторно проверяют условие перед каждым дочерним элементом.
Финализация комнаты и освобождение задания опроса стоят за пределами
блоков, которые могут пропустить действия после ошибки.
